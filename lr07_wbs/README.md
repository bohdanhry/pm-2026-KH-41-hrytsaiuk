## 2. Правило 100%: як перевіряли

Спосіб перевірки: скриптом порахував суму годин дітей для кожного вузла і порівняв з батьком. Окремо звірив кожен листовий вузол із переліком робіт у `schedule.csv`: жодного листа без роботи і жодної роботи без листа.

Робота, яку ледь не забули: доступ до вивантаження розкладу і роль диспетчера, вузол 1.5.2. Згадали на кроці залежностей, коли імпорт розкладу не мав чого чекати. Також додали управління проєктом, вузол 1.1, і приймальне тестування із замовником, вузол 1.4.3.

Що свідомо поза обсягом першого релізу:

- Фільтрація за викладачами чи аудиторіями, бо потребує окремої моделі даних про викладачів, якої в вивантаженні немає.
- Push-сповіщення про екстрені оголошення, бо це друга функція сповіщень з окремим каналом для навчальної частини.
- Вхід за університетським записом, бо перший реліз працює без акаунтів.
- Темна тема, налаштування нагадувань і експорт у календар, бо це комфорт, а не вирішення основної проблеми.
- Перегляд логів активності системи.

Цей список має збігатися з розділом «не робимо» статуту. Дві історії, фільтрація і екстрені оголошення, у `backlog.csv` стоять у REL-1 і суперечать цьому списку. Їх треба або перенести в REL-2, або дописати в WBS.

## 4. Критичний шлях

Дата старту робіт: 2026-11-02. Тиждень це п'ять робочих днів, свята не рахуємо.

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 70 |
| Ланцюг критичних робіт | T-02 → T-06 → T-10 → T-15 → T-16 → T-23 |
| Дата завершення за планом | 2027-02-05 |
| Строк мого варіанта, робочих днів | 70 |
| Різниця | 0 днів |

Ланцюг містить ще T-17, приймальне тестування паралельно з пілотом, воно теж має нульовий резерв.

Чи вкладаємось: так, упритул. Запасу в днях немає, будь-яка затримка на критичному шляху зсуває реліз.

Що з цим робимо: перша версія плану давала 91 день, фініш 2027-03-08. Три рішення скоротили її до 70 днів. Приймальне тестування йде всередині пілоту, а не після нього. Мобільна частина сповіщень робиться за узгодженим контрактом даних і не чекає на серверну. Офлайн-режим скорочений до перегляду збереженого розкладу. Обрана дата фіксована, обсяг різали. Ціна: офлайн-режим не оновлює дані без мережі, а приймальні помилки знайдуться в пілоті.

Робота з найбільшим резервом: T-21, 38 днів. Сценарії приймального тестування потрібні лише наприкінці, тому писати їх можна будь-коли після формату вивантаження.
